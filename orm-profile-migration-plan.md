# Migrate `orm.User` to `orm.Profile` (single-user storage first)

## Goal and scope

Replace `orm.User` with a persistent `orm.Profile` identified by a database primary key and a UUID. Preserve the former user's email, first name, last name, and institution; email is **not** an identifier or a unique constraint. The UUID of the configured profile (`PROFILE_UUID`) identifies its ORM profile row. Existing nodes, groups, comments, and authinfos retain their association with that identity. An ORM profile is distinct from `aiida.manage.configuration.Profile`, which still holds the connection and process-control configuration.

This PR migrates only a storage containing **exactly one** legacy user. Newly initialized storage gets one ORM profile matching its configured profile, including contact fields supplied during setup. No attempt is made to split a multi-user storage or create multiple configured profiles pointing to the same DOS path in this PR. Multiple users must cause an actionable error **before any destructive schema or configuration changes**; leave the old storage and user records intact. Handle a zero-user legacy storage explicitly (create an empty-contact ORM profile for its configured profile, if otherwise valid), with a test.

The configured profile retains its name, UUID, storage connection, broker settings and default-profile status. In particular, a migrated `sqlite_dos` profile continues to use the same directory; do not copy the database or objectstore. Do not introduce ownership-based read filtering: previously all users of one storage could access the same graph.

## Implementation sequence

1. **Undo the lossy user removal on this branch.** Replace the current `main_0003` (PSQL/SQLite DOS) and archive migration logic that stamps every record with one UUID and drops `db_dbuser`. Stop the config v12 migration from discarding `default_user_email`/contact options without a replacement. Replace the hidden, ignored `--email` setup option with one that persists contact information. Update the user-removal documentation accordingly. Since these revisions are not released yet, revise the branch's migrations rather than add a migration that can no longer recover dropped data.
2. **Define the persistent model and ORM API.** Add a `db_dbprofile` row with integer PK, unique UUID and non-unique optional email plus first/last name and institution. Expose `orm.Profile`, its collection and backend implementations for PSQL and SQLite DOS; keep config-profile and ORM-profile types unambiguous in code. Establish the invariant that the loaded configured profile's UUID selects its ORM row. New storage initialization creates that row; profile setup persists the supplied contact details. Specify how other entry points creating profiles (`presto`, fixtures) obtain blank/default contact values.
3. **Make migration lossless and fail closed.** Preflight *before* Alembic changes: determine the number of legacy users; reject more than one with a clear remediation message and no mutation. For one user, retain its PK and personal details (e.g. rename/alter `db_dbuser`), assign the configured profile's UUID, and migrate `user_id`/`aiidauser_id` relationships to that row (or backfill UUID references through the old FK before dropping it). Preserve the per-profile/per-computer authinfo constraint rather than collapsing authinfos to one per computer. For zero users create the matching profile row and fail if existing ownership references cannot be resolved. Keep the PostgreSQL legacy-Code rewrite after schema DDL to avoid pending FK trigger events. Respect SQLite batch-alter/foreign-key handling; check counts and FK integrity before and after.
4. **Coordinate config and storage safely.** A config migration cannot assume storage is reachable or perform an atomic transaction with the database. Keep legacy identity hints until storage migration succeeds, back up the config, and reconcile the configured UUID with the ORM row on each load/migration retry. Never silently create a second identity if the same storage is configured under another profile UUID. Do not treat a config-only upgrade as completion of the data migration; document recovery from a failed step. Revisit config version/schema and migration tests.
5. **Preserve archive semantics.** Archives may contain several authors even when a live DOS profile has only one user. Do not silently stamp all archive rows with one UUID or discard contact details. Either preserve each archived identity and map it during import, or explicitly defer multi-author archive conversion and reject those archives *before* modifying the destination. Test old archive upgrade, export/import and repeated import, not just live-storage migration.
6. **Wire remaining API surfaces.** Restore contact details where shown by CLI/REST/dump and update QueryBuilder joins, serializers, tests and fixtures that previously relied on `orm.User` or `profile_uuid`. Preserve provenance ownership without making email a primary key. Check configuration profile switching and authinfo lookup with the new ORM profile identity.

## Acceptance tests

- PSQL and SQLite DOS: legacy one-user storage retains all contact details, identifiers, node/group/comment ownership, authinfo contents and repository objects; migration is repeatable and a fresh storage matches the migrated schema.
- Zero-user legacy storage migrates safely; multi-user storage rejects migration without modifying its schema/data; config upgrade alone does not destroy the only mapping back to the original user.
- Setup with `--email` stores the value in `orm.Profile`; omitting it uses a documented default. Emails can be changed and are not unique identifiers.
- Switching/reopening the configured profile resolves the same ORM profile by UUID. Dump, archive import/export and CLI/REST contact fields do not silently lose identity data.
- Verify schema regressions for both backends and run targeted migration, ORM, CLI and archive tests (including a nonempty DOS repository) in CI.

## Future PRs: shared DOS and multi-user storage

- **Multi-user split:** create one configured profile per legacy user, each with a distinct UUID but the *same* storage connection and repository, and migrate FK ownership without restricting visibility. Define deterministic names/default-profile selection, broker/daemon behavior, collision handling and a retryable two-phase config/database migration. Explicitly opt in rather than silently splitting on upgrade.
- **Safe attachment to existing DOS:** provide a validated way to configure an additional profile against an already-initialized DOS directory without running normal `initialise()` (which deliberately rejects nonempty paths). Verify the repository UUID and schema; do not relax the new-storage safety check globally.
- **Shared-storage lifecycle:** prevent reset/delete of a DOS directory still referenced by other profiles; coordinate migrations, full maintenance, repository cleanup and backups across *all* profiles referencing that directory. `ProfileAccessManager` currently locks by profile name, not storage identity. Ordinary object writes and SQLite database writes have their own concurrency mechanisms, but do not form one cross-database/repository transaction; benchmark and document concurrent use before claiming shared DOS support.
- **Multi-author archives:** retain and resolve distinct author identities across export, import and storage migrations, including conflicts when UUIDs or contact information already exist.
